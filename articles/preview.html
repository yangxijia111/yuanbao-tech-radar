【元宝搜索开发者征文大赛】给毕设做一台技术雷达：8 路检索、10 组参数实测与一次噪声过滤复盘

作品阶段：可演示原型。 流水线已跑通、简报为真实生成，但尚未挂定时任务每日推送，因此不算「已用于日常工作」，更不是已上线服务。 方向：学习与创作 / 调研分析。 服务对象首先是做毕设的我自己，其次是同组做类似课题的同学。 文中所有数字、耗时、返回条数与链接均来自真实接口调用，未经美化；evidence/ 下的原始响应可逐条复算，密钥已脱敏。

一、需求从哪里来：一个学生开发者的资料困境

我是广东轻工职业技术大学的一名学生开发者，毕业设计是一款跑酷风格的休闲游戏：用 Unity 开发，要同时交付 WebGL 与 Android 双平台，且双平台帧率不低于 30 FPS；玩法是跑酷主体加道具触发的三种迷你游戏（切水果、音游、石头剪刀布），还要有 3 档难度、评分统计与 Top 100 排行榜。

这个题目最磨人的其实不是写代码，是查资料。引擎版本变更、WebGL 构建参数、Android 帧率优化、无尽跑酷的对象池与碰撞判定、音游的输入延迟校准、排行榜的数据结构——每一件事都要查，而答案散落在 Unity 官方文档、技术博客、学术论文和各种转载站里。原来的做法是开十几个浏览器标签，看到有用的就丢进收藏夹，或者把群里转来的公众号文章截一张图存着。

三个问题反复出现。第一，信息散：同一个「WebGL 内存优化」，官方手册、个人博客、二手转载各说一半，没人替我按来源归好类。第二，出处乱：收藏夹里往往只剩标题，链接和发布时间早丢了，想写进开题报告时根本不敢引用。第三，时效混：Unity 2022 LTS 与 Unity 6 的 API 差异、某篇两年前的优化建议是否还适用，靠肉眼判断经常出错。举个真实的例子，FindObjectOfType 在 Unity 2023.1 与 Unity 6 里已被标记弃用，而早期教程里还在大量使用它；这类「当时对、现在错」的资料，比搜不到更危险。

所以我给自己定的目标不是再写一个搜索框 Demo，而是做一台「毕设技术雷达」：按四个业务维度自动跑 8 路检索，输出一份分类整理好的 Markdown 简报，每条都保留原始链接、站点名和发布时间，能直接归档进毕设资料目录。判断它有没有用，标准也很朴素——我敢不敢把里面的条目引到开题报告里。

二、为什么需要搜索：制作阶段调用，不是运行时联网

先把边界说清楚：元宝搜索在这套工具里是制作阶段调用的，也就是我每次要更新资料时手动跑一次脚本；游戏运行时不联网、不调搜索接口。这个区分很重要，因为它决定了我要的是「可核查的资料清单」，而不是「低延迟的在线问答」，也决定了后处理应该把力气花在来源与时间上，而不是花在生成流畅的措辞上。

缺的是外部信息：引擎厂商的变更公告、官方文档的当前版本、别人踩过的性能坑、学术上对游戏评分模型的定义。这些不可能靠本地知识库或大模型凭记忆补出来，尤其涉及版本号与政策口径时，一句「应该是这样」代价很大。把检索结果当成可追溯的依据、而不是让模型凭记忆补答案，放在毕设开题这个场景里不是口号，是刚需。

不自己写爬虫的理由也很实际。SearchPro 返回的 Pages 直接给了 title / url / date / passage / content / site / score / favicon / pics，不用解析 HTML、不用猜发布时间；Freshness 把「近 30 天」「近 3 个月」「指定日期区间」做成了一等参数；Industry 能单独拉 gov / news / acad / finance 四个垂直域；Site 能指定或排除域名。对「出处必须可追溯」的资料整理来说，结构化字段比一个看起来很完整的答案更重要。

额度这块先交代清楚：腾讯云账号实名认证后，每个自然月有 2000 次免费调用；活动期内凭渠道邀请码在活动专区核销一次，本自然月提升到 6000 次，全版本通用。核销只能享受一次，多个邀请码不能叠加；个人账号的额度只能用在极速版与标准版，旗舰版仅企业账号可开。我选了标准版——极速版不支持 Mode / Cnt / Industry，后面那 10 组参数实测根本做不了。这个选型不是随便挑的，它直接决定了实验能做多大。

三、怎么实现：零依赖客户端、8 路检索式、三个必须容错的地方

3.1 从开通到第一次「搜索 → 结果」

流程按官方核销文档走：进入活动专区 → 立即开通 → 完成服务配置 → 返回控制台（等 3–5 分钟分配资源）→ 再次进入活动专区点「参与活动」→ 填邀请码提交 → 在控制台「概览 > 服务 API KEY 方式」创建 API KEY。明文只在创建弹窗出现一次，我把它写进 .env 并加进 .gitignore，全程没有出现在任何日志、报告和提交里。

鉴权我选了服务 API KEY 方式，请求长这样：

POST https://api.wsa.cloud.tencent.com/SearchPro
Authorization: Bearer <API_KEY>
Content-Type: application/json; charset=utf-8

{"Query": "三星堆的由来"}

官方提供三种接入：腾讯云标准方式（SecretId/SecretKey 加 TC3-HMAC-SHA256 签名）、服务 API KEY 方式、以及 MCP（https://api.wsa.cloud.tencent.com/Mcp）。前两种我都实现了（签名版纯标准库手写，作为备用路径），主路径用 API KEY。理由很实际：它只要一个 Bearer 头，整套工具零第三方依赖，拷给同学不用先配 pip 源，也不会因为 SDK 版本差异跑不起来。

第一次冒烟跑了两句查询。第一句用官方示例词「三星堆的由来」，HTTP 200，448.0 ms，Version=standard，10 条结果全部解析成功，前三条来自国家民委、人民日报、中国日报网；第二句换成「Unity WebGL 构建 性能优化」，735.4 ms，前三条全部是 docs.unity3d.com 官方文档。两句都是 10/10 条解析成功、0 条脏数据，但 date 字段覆盖率一个是 10/10，另一个只有 2/10。这个差异后来成了整篇文章最关键的伏笔：官方英文文档页往往不带可解析的发布时间，任何依赖日期的打分都不能假设字段一定存在。

3.2 8 路检索式，每一路都写明「为什么查它」

我没有把关键词一股脑塞给接口，而是按毕设的四个真实信息需求拆成 8 路，配置单独放在 radar_config.py，每路都带一句 why：

维度 检索理由 两路检索式与参数
引擎版本与兼容性 锁定 Unity LTS，版本升级会推翻既有构建配置 Unity 2022 LTS WebGL 平台 支持 变更（Freshness=m3）；Unity 版本 弃用 API 迁移 兼容性 说明（Freshness=y1）
双平台帧率与性能 验收硬指标是双平台 ≥30 FPS，需要可核查依据 Unity WebGL 帧率 内存 优化 30 FPS（Freshness=y1）；Unity Android 性能优化 帧率 稳定 实践（不限时效）
玩法与迷你游戏实现 跑酷主体 + 三种道具触发玩法的判定与输入方案 Unity 跑酷游戏 无尽生成 碰撞判定 实现；Unity 音游 节奏判定 输入延迟 校准
评分统计与排行榜 要交付评分统计与 Top 100 排行榜，需确认数据结构 游戏 排行榜 Top 100 数据结构 设计 Redis；休闲游戏 评分 统计 指标 设计 学术（Industry=acad）

这样拆的好处是，任何一路结果变差都能定位到具体业务需求，而不是笼统一句「搜索效果不好」。比如「玩法」维度要的是经典实现思路，强行限时效反而会漏掉好教程，所以这两路我都不传 Freshness；而「引擎版本」维度要的是变更公告，就必须收紧时效。参数不是越多越好，是要和检索理由对得上。

3.3 三个必须容错的地方

第一，Pages 不是对象数组，是 JSON 字符串数组。 第一次按 item.title 去取全是 undefined，必须逐条解析，还要对坏数据容错，否则一条脏数据能炸掉整份简报：

def parse_pages(raw_pages):
    pages, bad = [], 0
    for item in raw_pages or []:
        try:
            obj = json.loads(item)
            if isinstance(obj, dict):
                pages.append(obj)
                continue
        except (json.JSONDecodeError, TypeError, ValueError):
            pass
        bad += 1
    return pages, bad

第二，date 有多种形态且经常缺失。 实测见过 2024/09/20 14:03:32、2026-09-18 00:00:00，也可能是纯时间戳，或者干脆没有。我把日期解析单独做成函数，兼容七八种格式，解析不了就返回 None；所有「近 30 天占比」只统计有日期的结果，并且分子和分母一起写进指标，避免把「覆盖率」误读成「新鲜度」。

第三，score 的量纲并不稳定。 文档写的是 0~1，但传 Industry 之后实测最高到 2.7852。跨组排序前必须在同一次响应内做 min-max 归一化，否则带 Industry 的那两路会整体霸榜，跟内容质量完全无关。最终综合分是 rel * 0.6 + authority * 0.25 + freshness * 0.15，权威度用一张公开的域名白名单判定（unity.com、docs.unity3d.com、github.com、gov.cn、edu.cn、arxiv.org 等），规则就写在配置文件里，谁都能查、谁都能改。

四、得到什么：一份能逐条点开核对的简报

跑完 8 路，得到 80 条原始结果，覆盖 41 个不同域名。流水线先按归一化 URL 去重（剥掉 query、hash、www. 与尾部斜杠），再按维度分组、组内归一化打分，每个维度取前 4 条，输出 reports/2026-11-12.md。本次 80 条里没有重复 URL，去重逻辑一条都没删——这点我也如实记了下来，没有为了显得「去重有效」去造数据。

简报长这样：每条给出可点击标题、站点名、发布时间、接口原始 score 和综合分，下面附一段摘要。举几个真正在结果里出现、对毕设最有用的条目：Unity 官方的 Unity IAP 5 迁移指南（Unity，2026/08/05）、Android Developers 的 Unity Adaptive Performance and Android provider（2026/10/08）、以及 Play 游戏服务弃用时间表（2026/09/08，明确写了 v1 于 2027 年 5 月关停）。第三条尤其典型：如果靠收藏夹里两年前的截图，我根本不会知道排行榜后端依赖的服务有关停时间表。这就是「带来源和时间的清单」比「一段答案」值钱的地方。

五、实际效果如何：10 组参数实测与一次诚实的复盘

5.1 参数到底有没有生效

固定同一句查询「Unity WebGL 帧率 内存 优化」，每组只改一个参数，共 10 组、10 次调用。下表是从原始响应里直接统计的：

变体 条数 date 覆盖 权威源占比 近 30 天占有日期 score 均值 耗时
基线（仅 Query） 10 6/10 50.0% 0.0% 0.7743 725 ms
Freshness=d30 10 10/10 0.0% 100.0% 0.7578 619 ms
Freshness=m3 10 10/10 0.0% 50.0% 0.7615 614 ms
Industry=acad 10 4/10 40.0% 0.0% 2.676 533 ms
Industry=gov 10 10/10 10.0% 0.0% 0.7928 430 ms
Cnt=50 50 36/50 16.0% 11.1% 0.7719 838 ms
Site=docs.unity3d.com 10 0/10 100.0% 无日期 0.7505 521 ms
Mode=0 10 6/10 50.0% 0.0% 0.7743 288 ms
Mode=1 0 0/0 0.0% — — 503 ms
Mode=2 10 6/10 50.0% 0.0% 0.7743 363 ms

从表里能直接读出六条结论：

  1. Freshness 确实生效，但有代价。 d30 让有日期结果中的近 30 天占比从 0% 升到 100%，可权威源占比同时从 50% 掉到 0%。原因不难推：政府与官方文档更新慢，一周内的新稿本来就少，强行锁时效，捞上来的多是转载站。所以最终策略是按维度分档：版本公告用 m3/y1，确实时效敏感的才用 d30。
  2. Industry 会改变 score 量纲。 acad 组均值 2.676、最高 2.7852，gov 组最高 1.9199，都超出文档标称的 0~1。这也反过来验证了 3.3 节那层组内归一化不是过度设计。
  3. Mode=1 在标准版上正常返回、无错误码、结果 0 条，耗时还有 503 ms，明显是服务端直接短路。Mode=2 与 Mode=0 的条数、score 均值、权威占比完全一致，说明标准版下「混合」并没有额外拼进权威垂直结果。指望 Mode=1 拿权威信源是拿不到的。
  4. Cnt=50 条数生效，但尾部被稀释：条数 10→50，权威源占比 50%→16%。想让某个维度更全，换检索式比加大条数更划算。
  5. Site 不是「一定召回 0 条」。 我限定 docs.unity3d.com 后拿到了 10 条、权威源 100%，但 date 覆盖 0/10 —— 时效性打分在这一组会整体失效。这个观察比「Site 容易搜空」更细一层：它适合做「锚定官方站」的补充查询，不适合当通用过滤器。
  6. date 覆盖率波动极大：8 路检索里从 5/10 到 10/10 都有。任何新鲜度加权都必须对缺日期做保守降级，我在排序里给无日期条目固定 0.30 的新鲜度，既不奖励也不过度惩罚。

5.2 噪声过滤前后

结构化检索解决了「散」，没解决「权威」。过滤版简报里仍混着 perflint.dev、vectraplay.com 这类个人站与内容农场。于是我加了一层后处理，完全复用 Phase 1 缓存、0 次额外接口调用，做 v1（纯归一化排序）与 v2（加噪声过滤）对照：

指标 v1 v2 变化
保留条数 80 49 −31
Top10 权威源占比 0.0% 30.0% +30.0 pp
Top10 平均权威度 0.400 0.580 +0.180

规则共 5 条，全部可解释、可复算：免费托管域名（命中 2）、垃圾特征词（0）、摘要过短（0，因为本次摘要长度都在 719–803 字）、查询词零命中即跨语种跑题（4）、同域名限流（25，非权威域名每站最多留综合分最高的 3 条）。被过滤条目、命中原因和规则源码都留在 phase2_ab.json 与 noise_filter.py 里。

这里必须说清一个取舍：+30pp 主要来自「同域名限流」，不是垃圾内容识别多厉害。它同时砍掉了 blog.csdn.net 上 18 条可能相关的文章（该站原本一家占了 21 条）。这是控制单一来源霸榜的代价，规则需要按实际效果持续维护，不是一次写完就完事。

还有一层更值得写下来：10 条「查询词零命中」全部来自 Industry=acad 那一路的英文论文，中文查询词在这些标题和摘要里一个都不出现。如果按规则一刀切删掉，就会误伤真正的学术文献。所以我给学术域名设了例外：其中 4 条被过滤、6 条保留下来，这 6 条「差点误伤」条目单独列在报告里，把判断权交回给人。规则能解决重复和跑题，解决不了「这篇论文到底有没有用」。

5.3 耗时与成本是怎么测的

所有耗时都用 time.perf_counter() 在发起请求前与读完响应后各取一次，单位是毫秒，逐次写进 phase0_run.json 和 phase1_raw.json；条数、date 覆盖、权威源占比、score 均值都由脚本从原始 Pages 复算，没有手工填数。单次调用实测在 288 ms 到 926 ms 之间，18 次调用逐次串行发起，每次间隔 0.12 秒。

调用量方面：Phase 0 冒烟 2 次 + Phase 1 的 10 组 A/B 与 8 路检索共 18 次 + Phase 2 的 0 次，累计 20 次。按活动核销后的 6000 次/月算，占 0.33%；若按标准版刊例价 20 元/千次折算约 0.4 元，实际落在免费额度内为 0 元。这里的测量方法也写清楚：调用次数以脚本记录的真实请求数为准，不是估算。

六、边界与下一步

这套工具目前有四明确边界。其一，接口返回的是摘要而非全文，个别条目摘要与正文有出入，正式引用前必须点开原文核对，简报里也因此固定加了版权脚注。其二，权威度靠域名白名单近似，个人账号拿不到旗舰版的 authority_level，它能把官方站排到前面，但排不掉所有文库站。其三，噪声规则的限流会误伤同站好文，属于需要持续调参的取舍。其四，它现在只是手动跑的原型，没有定时推送，也没有做跨次运行的 diff 去重。

下一步有四件事：把 8 路检索挂到定时任务、只推送与前一日 diff 出的新条目；把 passage 交给大模型做「这条要不要改构建配置」的研判，而不是继续堆链接；Site 改成给每个维度配一条锚定官方站的补充查询；噪声规则从人工维护改成按「同域名连续 N 次被过滤」自动沉淀。做完这些，它才有资格从「可演示原型」变成「已用于日常工作」。
